# Cursor

Cursor has one Token Monitor-managed account list used by both tokscale self-sync and dashboard limits. Limits identity and local token history still remain separate outputs.

## Accounts and lifecycle

The credential store tracks multiple Cursor accounts and one active account. Desktop discovery can import the local access token without triggering a usage sync. Manually added session tokens and local access-token JWTs are normalized into the canonical form before storage.

Login, logout and sync share one lifecycle lane. This prevents an explicit account operation from racing the collector's background sync. Aborted queued work leaves promptly; a failed operation does not poison the lane. Tokscale subprocess timeouts and aborts request termination and wait for the shared close/forced-termination barrier.

Manual explicit sync allows Tokscale's dynamic budget of up to 1800 seconds plus 30 seconds for subprocess shutdown. Background collector self-sync keeps its 150-second budget and existing throttle/cadence; caller-supplied timeout budgets take precedence on both paths.

Only accounts added manually by Token Monitor may be removed from its UI. Desktop discovery remains ambient ownership.

## Self-sync and sessions

Cursor is self-synced: the collector supplies its one `SelfSyncThrottle` and tokscale resolver to `createCursorSelfSync()`. A credential change forces one targeted Cursor usage sync but does not restart the usage runtime.

Cursor's old CSV usage names Auto as `auto`; its JSON usage events name the same mode `default`. Token Monitor groups both under `cursor-auto` in usage, History graph, old device periods, and archived session/client/day replay. Keep this mapping scoped to Cursor because other clients may use `default` for a different model. A persisted Cursor collector anchor from before this mapping must be rescanned once so its broader periods cannot mix old and new model keys.

Included Cursor calls on the current weekly plan are listed by Grok's usage page, not by the cursor.com usage-event export. Billing recovery defaults off. The user connects it explicitly on each Cursor account in Settings; startup never opens a sign-in window. Each selected account uses a separate `persist:cursor-billing-<hash>` session and a versioned ledger under `userData/cursor-billing/`. The partition and ledger key derive from the Cursor account identity. Each downloaded Cursor item's `displayExtras.userEmail` must match that account's freshly authenticated Cursor identity before the row's identity fields are discarded. Missing or mismatched ownership rejects the entire download. A successful HTTP response by itself cannot establish ownership of an item. `query-billing-items` must run as a same-origin request inside the logged-in usage document: Electron's `session.fetch` was observed receiving a Cloudflare HTML challenge even with the session's login and clearance cookies. Page-load events can also precede the dashboard's authentication bootstrap, so initial failures receive bounded short retries; closing the window cancels pending retries. The dashboard window hides after a successful sync and stays alive for subsequent requests. This browser-session transport is separate from the credential-injected limits transport; no cookies cross into the widget renderer.

The live response holds rows in `data`, the model in `displayExtras.model`, and pagination in `pagination.hasMore` / `pagination.nextCursor`; the next request sends `cursor`. Product labels use the same whitespace and case normalization for ownership checks and row parsing, so every accepted Cursor label requires the owner check. Continue across pages with no Cursor rows. Deduplicate by billing-item id, never by equal timestamps/model/token counts when ids are available. A partial or looping pagination must not overwrite the saved ledger. Refreshes for the same ledger share one request, and older downloaded rows survive the rolling query window. Only normalized token rows, billing-item ids and hashed ownership keys are stored; raw emails and account ids are discarded.

Only explicitly connected accounts participate. When this desktop owns a usage collector and Cursor tracking is enabled, a serial background poll queries today every 30 seconds, bounded by local midnight and the next local midnight, and reconciles the rolling history every ten minutes. Only changed rows trigger a Today collection and history refresh; unchanged polls do not spawn native scans. App and Edge Dock manual refreshes await today's billing sync before collecting usage, while a failed billing fetch preserves the ledger and allows the other collectors to continue. Ordinary stats reads and settings/limits actions do not fetch billing. The background timer stops when the app quits. Account polling is serial and one failed account does not block another. Background session restoration is hidden; expired authentication is surfaced in Settings rather than by opening a window. Disconnect removes the account from collection, closes its window and clears only its partition's login data. Previously downloaded rows stay in that account's ledger and become available again only after explicit reconnection. Generation checks fence in-flight writes and callbacks after disconnect or shutdown. The old unscoped ledger and partition are left untouched and are never automatically adopted: users reconnect and fetch the rolling recovery window again, because the old ledger cannot prove its owner. This bounds local polling delay, not the upstream billing publication delay.

Only verified `product=cursor` rows are eligible. Native reconciliation is scoped to the account recorded in the cache's `_tokscale.accountId`, including archived caches; the active login cannot reassign an older cache's owner. For each UTC event day, match every native call against a distinct billing row by exact timestamp, normalized model and complete token vector. If every native call has a match, exclude those matching bills and retain the other bills. When any native call cannot be matched, native usage takes precedence for the entire overlapping day; usage for that day may remain incomplete rather than being guessed. Other missing days remain supplemented even if a sparse native export resumes later. An unreadable or unowned nonempty native cache prevents supplementation until ownership/coverage can be established. No account-wide latest-event cutoff is used. The full-period anchor retains a private signature of pre-today native coverage. A changed signature after sync forces serial Today/Month/All Time scans and a History refresh before matching bills are suppressed; unchanged coverage retains the single Today scan. This avoids dropping recovered historical calls from an older native anchor. Prompt, cached prompt, cache-write and completion tokens are summed. Included and paid/on-demand calls use the same accounting and reconciliation; this is an estimated catalog cost, not a statement of money charged. Included billed $0 is not the headline: apply the tokscale catalog estimate the same way native Cursor rows do, and leave missing rates unpriced rather than $0. Billing is projected into Today/Month/All Time on every collection, outside native delta anchors, including other clients' watch ticks and late historical backfills. Its daily graph is merged after native history retention, and its live contribution is excluded from that archive to prevent duplicate history. A successful dashboard sync immediately refreshes usage and history. Billing rows do not supply conversation ids or project paths. The headless agent has no dashboard session and leaves the ledger untouched.

The desktop also reads existing `logs/<run>/window*/output_*/cursor.hooks*.log` records for local Sessions and Projects. This installs no hook and therefore depends on Cursor already logging an executed hook. Cache only scalar identities, timestamps, model, workspace and token counters; never retain the input's prompt, transcript or email. Duplicate hook executions share a conversation/generation identity. A single workspace root supplies the canonical project identity, and `composerHeaders` supplies the conversation title. Missing/rotated logs remain missing evidence, not zero usage.

Native details do not add accounting, history, uploads or archive records. A scoped billing row may be assigned to a local turn only when the start and stop hook records' `user_email` hashes match that ledger's verified identity hash. The current desktop login cannot prove ownership of historical turns. Only the hash is retained; missing or conflicting per-turn identity leaves the local conversation visible with unavailable usage. A completed turn receives billable tokens only when its complete token vector matches the dashboard rows inside its start/stop interval, with no competing conversation or duplicate claim. Cursor's turn input includes cached tokens; dashboard input excludes them. Missing counters, incompatible vectors and ambiguous matches keep the real conversation/project visible with unavailable usage. Billing timestamps split verified usage into local Day/Month/All Time, and native accounting sessions take precedence in each period. Projects with only unavailable detail display unknown; a project with known usage from other sources retains that known subtotal. No account-level billing is distributed by proximity alone. These logs cannot recover per-session counts for failed turns that omitted counters.

Local project ids are shared across tools. Merge native project totals, client/model subtotals and unavailable flags instead of replacing another provider's entry for the same project. This local merge never adds accounting or wire records.

The desktop `User/globalStorage` directory is watched only for direct `state.vscdb` and `state.vscdb-wal` changes. In real-time mode, these events request a targeted Cursor cloud sync before the `--today` cache scan, using the shared ten-second source-event floor instead of the idle five-minute cadence. Smart mode consumes the signals at its next activity-gated interval tick; interval mode retains periodic sync. An event inside the floor retains a targeted catch-up; failures use the existing five-minute backoff. SHM changes are discarded because our own read-only credential/title queries can rewrite the wal-index. Other extension data is pruned. No hooks are installed, and desktop state is a refresh signal, not a token ledger: usage still depends on Cursor's cloud records becoming available.

The generated tokscale Cursor cache is not watched because Token Monitor's own sync writes it. `usageEvents.js` indexes live and archived cache events by account and conversation, invalidating only changed files. `sessionGuard.js` uses that index to retire legacy synthetic event ids when a canonical session supersedes them; ambiguous events do not guess.

The usage events carry conversation ids but no names. Session titles come from the local Cursor desktop `composerHeaders` table, joined by conversation id; releases predating that table are read through the legacy `composer.composerHeaders` key instead. The reader opens the database read-only, queries only the requested ids, and refreshes its title cache when the database or WAL changes. Sessions without a local header retain the normal client/model fallback.

The desktop Sessions list groups Cursor bot conversations into one Grok Bot entry, sorted among other sessions by its latest activity. A nonempty `sand-subagent-` id or positive `grok-bot-*` model usage identifies a bot conversation. All models in that conversation stay together, including Claude; an ordinary Cursor Claude or Grok conversation without either signal remains separate. Classification survives display model aliases and uses matching conversation ids across the available period snapshots. Each Electron stats snapshot includes a compact bot-id projection for current DAY/MONTH conversations, checked by direct lookup in its captured local history without completing or transferring the all-time session list. This evidence refreshes with stats even if TOTAL has never been opened; immutable source maps reuse cached identity results. Without source evidence, a UUID-only Claude conversation remains independent. Grouping is an Electron presentation projection: period totals and original session identities are retained, and the group lists each run's title, model, time, calls, id, tokens and cost in newest-first order. The displayed count is activity records (one per distinct source session id in the selected period), not Grok chat rooms or individual billable calls. The source exposes no parent-chat mapping, so no parent conversation is inferred, and Cursor runs have no transcript-detail action.

Grok Bot activity records do not infer a running turn from the ten-minute usage-recency window. Without an explicit turn boundary they retain their last-activity time and usage, but show no running or completed indicator and do not enter running-only lists. A confirmed open or completed local turn still uses the normal bounded state rules. Resolve bot membership before activity across period snapshots and display aliases, and retain it and the distinction between missing and false `turnEnded` through Home and Edge Dock projections and paint-time checks.

For known usage conversations, the same read joins `cursorDiskKV`'s `composerData:<id>` by a matching embedded `composerId` and extracts only turn-state scalars. Modern headers outside the running window skip the larger composer payload unless usage is still recent; a resumed header's DB/WAL change admits it again. Cursor serializes local `generating` as `aborted` with `unfinishedRunAt`; that combination keeps the turn open, while `completed` or `aborted` without the marker stops the running indicator on the next collection. Definitive unknown/malformed reads clear earlier boundaries; transient read failures retain the last confirmed boundary in the existing per-database cache across collections and remain retryable even when a new title was read successfully. Partial Today passes retain other periods' boundaries; only a complete Today/Month/All Time set prunes sessions absent from usage. A missing or unknown result in an earlier candidate database cannot mask a later candidate’s valid boundary. Future editor timestamps do not extend activity recency. The existing time window still bounds an unfinished marker left after an editor crash. This does not discover zero-token conversations, install hooks, or change token/cost accounting; no additional watcher or timer is needed.

## Limits

Every enabled saved account is probed independently. Stable identity prefers the canonical API subject; opaque local fallback ids remain distinct rather than merging unrelated accounts. API email is presentation metadata, not the only identity key.

The dashboard mapping preserves separate official model pools, legacy request plans, enterprise/team pooled usage, optional Grok Bot allowance and on-demand spend. Never synthesize an overall total by summing model pools. Grok Bot is best effort and must not fail the main account row. A zero uncapped spend is hidden; positive uncapped spend remains visible.

Unified plans (The X Subscription: Plus, Premium, Super and unified Ultra) are detected by `get-plan-info`'s `isMerged`, or by the sand status's `isUnified` when plan info is unavailable. They show one `Included usage` row. Its percentage is `GetCurrentPeriodUsage`'s `planUsage.totalPercentUsed` when the session access token can call that RPC; when that value is unavailable, a sand status with `isUnified` supplies `usagePercent`. If neither source has a valid percentage, only an explicitly monthly period may fall back to `usage-summary`. Weekly, missing/unknown periods and sand-only unified plans keep the percentage unknown instead. The current-period call is best effort and must not fail the account row. The row defaults to weekly, including when plan info or its period is missing or unknown, and uses `includedUsageResetsAt` when available, otherwise leaving the reset unknown. Only an explicit monthly period follows the billing cycle. The pool is shared with Grok and Grok Bot, so the separate Grok Bot row and the two model pools are suppressed. `get-user-prepaid-billing` is requested only for unified plans; a positive `availableCents` becomes a `Prepaid balance` credits row. Legacy on-demand fields never produce an `On-demand spend` row for unified plans, which use prepaid credit instead. These dashboard RPCs answer in proto3 JSON: int64 values are decimal strings, enums are full names, and zero values are omitted, so an absent `isMerged` means legacy and an absent balance means zero. `usage-summary` was verified live on a legacy account. On a live unified Premium account it stayed at an explicit 0 for the calendar month while `GetCurrentPeriodUsage` matched the weekly percent shown in Cursor settings.

`Included usage` is Token Monitor's display label. Missing total usage stays unknown: do not synthesize zero or combine the separate model-pool percentages into a unified total. An explicit zero from current-period usage or unified sand remains valid. Only an explicitly monthly plan may fall back to `individualUsage.plan`'s total percentage or complete used/positive-limit pair, including zero. Unified plans never substitute `individualUsage.overall` or `teamUsage.pooled` for the seat's included percentage; those legacy aggregate fields do not establish its weekly allowance. Without a known percentage the included row is omitted, while independently available prepaid credit and the separate billing `Team pool` remain visible. Legacy aggregate fallback is unchanged. Plan-info timestamps outside the JavaScript Date range become unknown without failing the account probe. The monthly date fallback currently uses the usage-summary billing cycle before plan info; the included percentage follows current-period usage. The reset date still comes from plan info.

Account-scoped enable/disable affects limits collection only. The active tokscale account and self-synced history are managed by the explicit Cursor lifecycle operations.

If both plan-info and sand lookups fail, the plan type stays unknown: a successful legacy response with omitted proto3 false flags is different from a failed lookup. Unknown plans do not expose `Requests`, `Cursor Models`, `Other Models` or `Overall`, even when usage-summary reports zero used, and invalidate those labels in that account's last-good cache. Independently reported team pool and on-demand spend remain available; with no current windows, the provider reports unavailable. Previously confirmed unified windows follow the shared [partial-result retention contract](../architecture.md#limits-collector). This does not change token-event synchronization or recover missing token history.

The best-effort current-period RPC has a wall-clock deadline of at most five seconds, preserving a shorter configured timeout. This covers DNS, connection setup and response reads, destroys the request on expiry, and retains parent cancellation. The deadline timer and parent listener are cleaned up when the call settles. On timeout, normal percentage fallback still applies; this is a deadline for this RPC, not for the entire account probe.
