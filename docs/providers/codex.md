# Codex

Codex combines a tokscale-backed usage client, local rollout enrichment, supplementary local-executor observations and a multi-account limits provider. Keep usage and limits separate even though they share the `codex` id.

## OpenCodex model attribution

Tokscale can resolve an OpenCodex Responses combo selector to the physical model using `~/.opencodex/usage.jsonl`, or `OPENCODEX_HOME/usage.jsonl` when configured. It requires matching successful attempt, token and timing evidence; ambiguous rows retain the selector. This relabels existing Codex usage without adding token rows. The ledger is consulted during normal Codex scans; ledger-only changes have no dedicated watcher and wait for the next scan, with older periods reconciled by a full scan.

## Dots local execution

A class of Dots-created local Work/Codex tasks currently exposes live App Server counters without writing a local rollout. `localUsageSource.js` observes those counters through the hosted desktop App Server, using the live `CODEX_HOME/auth.json` login. A task qualifies only when its single execution environment matches a running **local** `codex exec-server --environment-id` process and its source is `codex_work_cca` / `aeon_child`; cwd alone never proves device ownership. Cloud coordinators, another computer's executors, ambiguous environments and tasks with native rollout paths are excluded. Normal rollout collection continues unchanged.

The executor command can include assignment-valued global `-c` / `--config` overrides before `exec-server` (the desktop adds `forced_login_method`). Windows process command lines can retain backslash-escaped quotes in those values. Match those options explicitly; searching for `exec-server` anywhere in a command line would admit wrappers or unrelated commands. Allow for PowerShell/CIM cold start during Windows discovery; the probe requests termination after 15 seconds on Windows and two seconds elsewhere, retaining bounded termination escalation and cancellation. Process arguments and environment IDs are never logged.

Observation is experimental and disabled by default. The widget's Collection → Codex panel exposes separate “Collect Dots usage” and “Show Dots usage” switches. Collection is off by default; visibility is on. The persisted `codexDotsEnabled` collection selection takes effect through usage-runtime reconfiguration without restarting the app. `TOKEN_MONITOR_CODEX_LOCAL_USAGE=1` supplies the initial widget default when no saved selection exists; a saved selection takes precedence, including OFF. Turning observation off preserves the durable ledger and previously collected totals. `codexDotsVisible=false` excludes this device’s supplemental ledger contribution from periods, sessions, projects, history and outgoing device totals without stopping observation or deleting rows; showing it again reconstructs the contribution from the ledger. This does not hide Dots contributions reported by other devices. Collection changes rebuild the usage runtime. Visibility refreshes its projection and history in place, preserving the observer connection, lease and subscription baseline. In-flight results under the previous visibility are discarded, and a hidden replacement collector replaces carried history. If a visibility history refresh fails, the old projection is cleared until a successful refresh rather than continuing to publish hidden Dots usage. Both selections remain local to this widget. With no opt-in, no executor probe, socket or discovery timer is created. Packaged widgets do not read the project `.env`. The separately launched headless agent keeps its environment opt-in and does not read desktop settings: opt in each intended observer separately, with the same `TOKEN_MONITOR_SHARED_DIR` (or the normal shared directory) and Codex home. The widget and resident agent share a transactional 30-second renewable observer lease; the widget yields only when an enabled agent renews its observation intent and the existing agent PID is alive. An agent with this source disabled does not silence an opted-in widget. A stopped observer releases its lease; dead processes or expired leases permit takeover. One-shot collection only reads the durable ledger. Enabled observers probe every 30 seconds after confirming no local executor exists (no remote connection), and every five seconds with one. Ownership standby also retries every five seconds without probing or connecting, so an agent waiting for the widget to release its lease does not inherit the no-executor delay. Discovery checks every five seconds and live changes use the collector's existing bounded debounce. For the headless agent, `TOKEN_MONITOR_CODEX_LOCAL_USAGE=0` stops observation on the next launch without erasing already collected usage. The source uses the existing undici dependency with standard proxy environment variables and `NO_PROXY`; unlike Electron limits fetches, this worker-owned WebSocket does **not** inherit the OS proxy. It never starts turns, changes thread configuration, answers approvals or requests quotas.

Source events use the collector's bounded watch debounce. Smart mode records activity; interval mode keeps its configured cadence. Stopping the collector closes the observer connection and fences late callbacks.

`codex-local-usage.sqlite` in the shared data directory stores only counters, request identities and session/project metadata. Transactions and cumulative checkpoints deduplicate notifications across reconnects and the widget/agent. The first valid counter notification per subscription/reconnection establishes a baseline without recording usage, even if it includes an old last request. This may miss the first new request after connection, deliberately preferring undercounting to historical backfill. Later observed requests receive the local observation day and the project reported by the current thread metadata. A model is used only when a `model/rerouted` event supplies both that turn id and destination model; otherwise the model remains `unknown`, including after reconnect. Cumulative gaps are never attributed to the current session model; server execution timestamps and historical model splits are unavailable. Session rows retain `usageSource: "codex-dots-local"` and `usageCoverage: "observed-only"` through normalization and sync. These fields describe incomplete coverage, not a measured percentage. A pre-observation cumulative prefix and gaps while offline are not backfilled. RPC input includes cached input and RPC output includes reasoning; convert to canonical exclusive input and inclusive output, then to the disjoint Codex buckets expected by the shared Tokscale decoder. Pricing uses the same catalog lookup as other locally parsed usage; unavailable bucket rates contribute no amount to the known `costUsd` subtotal and carry explicit `unpricedTokens` counters. The UI shows the missing token count rather than treating it as free usage. These are catalog estimates, not subscription billing. The current desktop protocol's `Turn` has no model field, and `Thread.model` is explicitly current/latest configuration rather than per-turn execution telemetry. Resume/read configuration, parent creation parameters and safety-buffering UI hints therefore cannot fill an unknown execution model, especially after attaching mid-turn or reconnecting. No historical ledger models are rewritten.

These requests appear under the existing `codex` client and use the actual thread id (not an inherited fork `sessionId`), the stored task name and `projectIdentity(cwd)`. Today/month/allTime and history consume the same ledger. If the native history scan fails and no nonempty retained native history is available, history is omitted from the update to preserve the previous complete device history; a Dots-only replacement is not published. A successful empty native scan can still publish Dots history. Native rollout sessions take precedence on identity overlap: the complete supplemental contribution for that thread is excluded from periods/history/detail, including previously recorded rows. This conservative whole-thread replacement can lose supplemental coverage if the rollout contains only part of the thread; merging unverifiable request identities would risk double-counting. Supplemental usage stays out of generic client, session and daily-history archives, so native replacement cannot resurrect it from a retained maximum. Client snapshots exclude explicitly identified ledger sessions on capture and normalization, including older snapshots with session provenance. The request ledger already provides retention, so `codexLocalSessionKeys` prevents a second copy in the generic session archive and is removed from sync payloads. Sync bounds session detail, so the widget cannot subtract Dots from externally reported agent aggregates without sufficient session provenance. Session details show observed token entries; conversation text and tool content are not collected. Titles stay local under the existing sync privacy rules. Hosted environment metadata is a desktop extension; connection/discovery failures retry with bounded backoff and leave native collection available.

Manual acceptance: run the updated widget with the experimental environment opt-in and Codex tracking enabled and the desktop local executor connected, ask Dots to create or continue a local project task, then verify its title/tokens in Sessions and its directory label in Projects. Restart Token Monitor and verify the same totals remain; continue the task and verify only the new consumption is added. Usage before observation began is deliberately outside this acceptance scope.

Aggregate collection reuses cached catalog prices and performs at most four uncached or expired model lookups per tick, with a 1.5-second command timeout each. Pending models rotate across ticks so failures, cache expiry and eviction do not prevent later models from being queried. A deferred refresh or failed pricing command retains a previously successful price from the same revision; command failures retry after 30 seconds. A successful lookup that explicitly returns no pricing replaces the old rate with missing-price state. Models without a successful cached rate remain explicitly unpriced. Token counts are unaffected. Successful prices are cached for five minutes and missing prices for 30 seconds, partitioned by pricing revision; a changed revision never reuses an old price.

Dots session details preserve each observed request's model and token buckets through the Worker message boundary. After the detail Worker returns, main reads the current custom-pricing/binary revision and resolves at most 16 distinct known models per open/refresh through the existing `tokscale pricing <model> --json` catalog lookup (1.5-second command timeout each); only model IDs are passed, without thread IDs, counters or conversation content. Tokscale may refresh its public pricing catalog; this is not model inference. Detail uses the same revision-keyed cache logic and command-failure fallback as aggregate pricing: a failed command retains the last successful same-revision rate, while a successful missing-price response clears it. Caches are thread-local: the usage Worker and main do not exchange prices, so a first detail lookup without a successful main-thread cached rate can still be unpriced. Detail refreshes still query the bounded model set. Native session details do not probe this pricing revision. Unknown models are never looked up. Each valid bucket rate contributes to the known subtotal while only missing-rate buckets are marked unpriced. No session subtotal is proportionally distributed onto Dots requests. Exchanges and turns preserve missing-price counts through grouping, period filtering and renderer adapters. This does not add actual-model evidence or change the raw ledger.

## Session metadata and context

The rollout index tracks native `request_user_input` calls by `call_id`; a matching result (including an error), new turn, completion or abort clears waiting. Only `waitingForInput` is published, without question content or call ids. Transcript freshness bounds this signal to ten minutes; it does not prove client liveness. Native approval waiting and asynchronous questions require a reliable client-owned pending/resolution source. Shell escalation arguments, an asynchronous `accepted` result and model completion cannot establish whether a UI request is pending.

The read-only `sessionActivity.js` adapter also reads T3 V2 requests. Match `nativeThreadRef.nativeId` to a verified rollout `session_meta.id`, then join the request through its execution node to the current run. Read the complete first JSONL line in chunks, up to 8 MiB; an incomplete or oversized header never establishes identity from the filename. Approval, elicitation and question requests need answerable pending evidence and a validated server incarnation. Resolved or retired requests clear waiting; live requests require an active run, while same-incarnation message-answerable questions may outlive model completion. Terminal idle uses the latest run completion or message-question resolution time without renewal and yields to newer transcript activity; missing or expired completion evidence falls back to native state. Missing or incompatible stores clear earlier observations to `unknown`. This does not attach to the app-server transport.

Bounded native catalog and current/previous date-folder discovery supplies local-only pre-token rows. Unarchived usage identities take precedence within each period; rows remain outside totals, anchors, archives and sync. A fresh resumed rollout also projects its protocol state onto existing usage rows in other periods, preserving their token/cost values and avoiding duplicate Home/Dock rows. File fingerprints and snapshot-scoped caches avoid repeated discovery, with invalidation on source or candidate changes; process identity and T3 pending requests are read afresh. Discovery never recursively scans history, although an unknown historical rollout alias may require an on-demand accounting-map lookup. Multi-UUID filename hints only admit candidates; the first metadata record still verifies identity. Completed transcript observations use the file timestamp rather than renewing an idle clock. The [shared activity pipeline](../architecture.md) owns event refresh, metadata patches and thirty-second expiry; remote observations renew only on ordinary publications. Historical archives omit both transient fields.

`sessionMetadata.js` joins rollout sessions to Codex's thread databases and, for T3 Code sessions, T3's own thread catalog. T3 drives the same harness but stores generated titles separately; a Codex-only lookup can otherwise fall back to the first user message. Attachment markup and agent boilerplate are stripped before display. Background reviews keep their `sessionKind` rather than masquerading as ordinary chats.

Native parent links come from the scan: the tokscale build resolves a subagent's or background review's parent thread to the rollout session id it keeps for that period (the thread's first rollout, else its earliest surviving continuation) and reports it as `parentSessionId`; human forks get none. Every link is kept and synced, reviews included. Updated desktop Sessions, Home and Edge Dock group visible linked members, while reviews stay in their one global group. Missing parents remain standalone. Review classification relies on the Codex thread database; if it is missing or unreadable and no retained classification is available, a review can be grouped as an ordinary subagent. This limitation is accepted.

A shared bounded first-header reader verifies `nativeSessionId` for both accounting and pre-token rollout metadata. It caches only path fingerprints and IDs, retaining historical entries so serial all-time scans do not repeatedly parse unchanged headers. Desktop Sessions, Home and Edge Dock use it to present continuation files as one conversation while preserving every accounting key and detail route. Continuations keep the main role and do not inflate subagent counts; filename hints alone do not establish this identity.

T3-owned delegation adds links independently of title precedence through the shared relationship reader described in [the architecture guide](../architecture.md#session-relationships). Native scan links take precedence.

The shared read-only reader in `src/shared/t3SessionMetadata.js` handles T3 discovery and catalog lookup; the Codex adapter retains its own title precedence and rollout-ID expansion. T3 V2 uses `statev2.sqlite`: join `orchestration_v2_projection_threads` to its provider-thread rows through `thread_id`, then match `payload_json.nativeThreadRef.nativeId` to the Codex rollout identity. Never match `provider_session_id`, which can be shared across conversations, or restrict a thread to its current default provider: earlier Codex runs remain valid after a provider switch. A V2 native-ID match is authoritative across all discovered stores, even when deleted or carrying an empty/placeholder title: it suppresses retained V1 tables in the same database and the legacy `state.sqlite` cursor join. Legacy titles are used only for IDs absent from V2. Both stores are read-only, and a genuine Codex-generated `name` still takes precedence.

Rollout lookup supports `.jsonl` and `.jsonl.zst` in `sessions` and `archived_sessions`, retaining the same suffix-free accounting key. Plain JSONL takes precedence over its compressed copy; archived files remain detail/metadata sources rather than pre-token live discovery roots. Compressed reads use Node's built-in Zstandard decoder, accepting complete concatenated frames with at most 32 MiB compressed input, 64 MiB total decoded output, a 64 MiB decoder window and 4096 frames. Invalid framing, truncated frames, checksum failures and oversized compressed files yield no verified identity/state and a detail read failure; partial decompression is never published as complete usage. Without a frame checksum, structurally valid content corruption is not detectable by decompression alone; records still pass through the existing JSON/schema checks. Compressed files are decoded again when changed, while plain JSONL retains its append-only reader. Metadata uses the existing decoded head/tail bounds, and detail keeps its 16 MiB per-record bound. Fallback legacy-key discovery is bounded to depth 32 and 100,000 entries across both roots; dated rollouts use direct lookup. Existing plain-file symlink lookup remains supported, while compressed-file reads require a regular, non-symlink file. Tokscale remains the token-counting authority.

`sessionContext.js` reads the newest rollout `token_count` event. `info.last_token_usage` is current occupancy and `info.model_context_window` is the actual per-session capacity; cumulative `total_token_usage` is never occupancy. Context, turn state and prompt-cache observations share one decoded session index. The initial scan reads at most the newest 1 MiB for context/cache and extends backward up to 8 MiB only to find a turn boundary, without rereading overlapping bytes. Subsequent append-only scans read only new bytes in bounded chunks and retain the accounting identity and last observation across ticks. Unchanged files reuse the index; replacement, truncation or same-size rewrites reset it. Oversized non-metadata records are skipped with bounded retained memory.

Do not replace the transcript-reported window with a model table. User configuration can change the window for the exact sessions being measured.

The title query also reads the optional Codex thread `reasoning_effort` column, including for historical and untitled sessions; older schemas remain supported. For recent sessions, the same bounded transcript index reads `turn_context.payload.effort` (or the legacy `reasoning_effort` field) before any token accounting arrives and overrides the catalog setting. A new `task_started` clears the previous effort; missing or malformed new configuration stays unknown rather than inheriting a previous turn, model-name guess or global default. A bounded cold read leaves effort absent until it observes configuration in its metadata range or a new turn start; completion alone supplies no setting evidence. Age or a failed transcript read alone does not clear a saved setting. This adds no transcript reads or polling beyond the existing reader and thirty-minute gate. Pre-token native rows carry the setting from their existing activity read, including when replacing an archived row in Sessions; the activity-only patch for accounting rows still carries activity state, not context or effort.

The optional `reasoningEffort` snapshot follows fresh Today metadata into anchored periods and is retained in session archives. An unchanged observation with the same `lastUsedAt` can recover its saved setting after a catalog miss; an explicit clear or a newer observation never falls back. Home, Sessions, Edge Dock and the Notch panel share the model/effort presentation. Effort is plain text without a tooltip, remains visible after context/cache expiry and for archived sessions, and disappears only for an unknown setting. For grouped conversations the latest main continuation owns the effort, independently of the group's cumulative model counts and child settings.

Rollout filenames are transcript lookup keys and can contain multiple UUIDs; do not treat every UUID as a resumable conversation or assume a fixed UUID position. Session Details takes its copyable identity from the first `session_meta.id` during the existing on-demand transcript parse, without an extra read or background preload. A multi-UUID key has no copyable ID until that metadata is available. This display identity never replaces the usage/grouping key.

Cache warmth is an optional `promptCache: { observedAt, ttlSeconds }` estimate from that shared rollout index; it adds no separate file read or JSON parse. Valid cache read/write activity starts a fixed 30-minute display estimate regardless of the model name or route, including third-party and custom APIs. This is a product estimate, not a reported Codex or provider TTL; actual cache retention can differ. Cold responses, model changes and compaction clear it. Repeated unchanged `token_count` accounting never refreshes the anchor. The anchor is a response observation, so remaining time may be overstated; quota accounting and successful reuse are not implied. Home, Edge Dock and Sessions share one metrics slot: recent context takes priority, with the context token/window counts and cache countdown available in the shared detail tooltip by hovering its bar or percentage; then a still-valid cache estimate appears after 10 minutes of inactivity, with the last recorded context counts still available on hover. Turn completion alone clears neither reading; the cache countdown ends at the observed TTL.

## Output-rate timing

Codex can persist `token_count` after local tools finish. Its timestamp is therefore not always the response completion time. New scanner support must pair `token_usage_record.usage` with the same accepted response counters before using its timestamp as completion, and derive the start from request boundaries without moving it forward when an asynchronous tool result arrives during model output. Older records need a conservative event-based estimate; missing, mismatched or non-positive timing must preserve tokens while contributing no performance sample. Never subtract a sum of tool durations: parallel tool execution and model output can overlap.

Keep rate timing independent from the existing session/activity span, including through incremental state serialization and cache migrations. The UI describes an estimated output rate, including first-output waiting, rather than pure model decoding. The vendored binary determines which timing behavior is available; app-side support alone does not update the scanner.

## Limits sources

The live account normally reads the ChatGPT/Codex backend with the current `auth.json`. The configured `chatgpt_base_url` selects the matching backend path family. The app-server RPC path is a fallback, not an interchangeable authority.

For a managed account, RPC output is usable only when the isolated auth snapshot is scoped to that account's selected workspace. Otherwise the explicitly scoped OAuth request must succeed. A transient OAuth failure may use a correctly scoped RPC reading; an unscoped live RPC must never be published under a managed workspace.

The live system account stays visible alongside enabled managed accounts. Composite identity keeps same-email workspaces distinct while collapsing the live and managed observation of the exact same login. Managed-account hydration must preserve local collisions rather than silently coalescing them.

Reset-credit data supplements quota when available. Empty quota can receive one bounded retry for plans expected to expose windows; do not turn absence into zero.

Plan labels come from the quota response's plan type. Display `prolite`, `pro` and `promax` as Pro 100, Pro 200 and Pro 500, the names Codex's status view uses for those tiers. The numbers are the monthly price, not a usage multiplier, so a tier name never implies a fixed quota multiple.

## Login and account switching

Only allowlisted `auth.openai.com` authorization/device URLs may be opened from CLI output. Command discovery and Windows quoting are part of the provider contract because Store/npm installations resolve differently.

Switching the system account rewrites the live auth material for the selected workspace. The write is atomic and identity-checked; UI controls serialize the operation and refresh only after it settles. Managed credentials remain in the main-process store.

## Reset forecast

The optional reset forecast is display enrichment from `codex-resets.com`, not quota authority. Its `active_watch.level: strong` signal can be valid with a null chance percentage; the expiry remains the validity boundary. It has independent success/error cache durations and bounded fetch time. A forecast failure must not alter the provider's real windows.
