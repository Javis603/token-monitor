## Sources and resource pools

MiniMax Code OAuth and the configured API key are independent lanes collected together. `minimaxBillingMode` selects only the API key's billing type (`token-plan`, the historical default, or `api`). Code is detected from the current local login regardless of that selection. Adding or clearing a key never selects or signs out Code. Key prefixes do not override the selected billing type; Token Plan and API billing never fall back to each other. `MINIMAX_CODING_API_KEY` remains the existing environment credential; no new environment credential is auto-discovered.

| Lane | Credential | Readings |
| --- | --- | --- |
| Token Plan | API key with `token-plan` selected | Quota authorized by that key, with the existing legacy Coding Plan fallback |
| API | API key with `api` selected | API wallet balance and optional server-reported cash Spend |
| Code | Current local MiniMax Code OAuth login | Code points and applicable Code plan quotas |

M Plan and retained Token Plan subscriptions have distinct benefits; retaining Token Plan or upgrading to M Plan is a server-side subscription choice. Their keys use the subscription quota reader, but a shared endpoint does not prove that keys are interchangeable, that an old key survives an upgrade, or that one key can observe two subscriptions. The compatibility setting `token-plan` selects the supplied subscription key's quota reader, not a product generation or a combined allowance. The `5h` and `Weekly` windows constrain the credential's current subscription; endpoint paths containing `token_plan`, the authentication source and the mere presence of those windows do not identify its generation or prove separate pools. Use the matched current subscription's type/title for that distinction, never the catalog's new-plan availability flag. Do not create an additional M Plan lane or add overlapping observations as extra allowance.

The producer of a request, the credential used to observe it, and the resource paying for it are different facts. Never assign cost from the client name, login method or token count. A Code action may consume quota, points, vouchers or cash; use the relevant server reading.

Code points use `CREDITS`, never CNY/USD. Membership's `op_credit_summary.total_remaining_amount` already combines purchased and gifted points: component balances must not be added again or emitted as independent balances. Purchased points are shared between Code and Open Platform; gifted check-in points are Code-only. Plan quotas and the pay-as-you-go cash wallet remain separate pools. Eligible Code points can cover usage after a plan limit when the user's fallback setting allows it; grants are consumed by expiry order, not an assumed paid-first or gifted-first rule.

## Wallet and Spend

API wallet balance comes from `/account/query_balance.available_amount`, including usable vouchers, rather than `cash_balance` alone. Zero and negative balances are valid; a missing or nonnumeric amount is unavailable. Balance and cash Spend measure different things and must not be subtracted to reconstruct transactions.

| Spend field | Server source |
| --- | --- |
| Today | `/account/amount`, dated `aggregate=true`, `consume_cash_after_voucher_sum` |
| Week | The same aggregate over seven calendar dates including today |
| Month | The same aggregate from the first calendar date of the month |
| All time | `/account/query_recharge.cash_total_usage`, with the console's `page_num=1&page_size=10` |

Periods use the console's calendar-date filters. Bills refresh daily and can lag the current wallet. All time means MiniMax's reported cumulative cash usage; the endpoint does not establish complete lifetime bill retention or real-time settlement. Cash Spend excludes voucher-funded consumption. Do not replace a valid post-voucher zero with `consume_cash_sum`, add voucher `used_amount`, substitute recharge totals, or sum rounded rows from a partial page. Voucher summary counters are not consumption totals for the selected issuance dates.

These are replacement snapshots, not increments. There is no MiniMax local Spend ledger, balance-delta fallback or tracking baseline. Optional Spend reads use the same selected key, resolved region and injected transport as the valid balance. A failed, denied or malformed optional result leaves that figure unknown without invalidating the balance, changing region or selecting another credential. Save-time probes skip Spend enrichment.

Code OAuth does not query the API wallet or cash-billing endpoints and never borrows the retained API key. Its status and points are independent of API credential failures. A Code action's payment pool does not establish which API credential can observe it: same-group evidence alone does not prove complete cross-key or team coverage. Do not automatically merge these lane identities or assign API Spend to Code.

OAuth and a Token Plan key can observe the same subscription's quota. Those readings are separate observations, not additional allowances; do not add them together or infer common ownership merely because their limits match.

## OAuth ownership and interoperability

Discovery follows the [mcode data-directory rules](mcode.md), using `auth/prod/{cn,en}/mcode-public`. Code discovery checks China then International independently of the API region setting. Resource requests and delegated renewal use the discovered namespace’s region. Each namespace contains one current login, not a managed account list. Local record keys identify storage, not the user. Preserve unrelated records and reread credential/state files rather than retaining a stale lease. Only file-backed official credential/state formats are supported.

Select exactly one `workspace_type: 0` personal workspace through `POST /matrix/api/v1/user/get_user_extra_info`; workspace ID `0` is valid. Pass that workspace explicitly to membership. Missing or ambiguous personal workspaces are unavailable; never change the official client's default workspace. Identity prefers the workspace's `op_group_id`, then membership's. A malformed membership total falls through to the workspace balance, then the membership scalar. A present malformed workspace balance does not.

Plan requests require a group and a plan indicated by `has_token_plan` or `token_plan_tier`; `has_valid_subscription` is unreliable. Code uses the platform `remains_percent` endpoint with `X-Group-Id`: its percentages are used amounts, unlike the API-key endpoint's remaining percentages. Video uses that endpoint's `current_interval_used_count` and `current_interval_total_count`; the legacy endpoint's `current_interval_usage_count` has different semantics and must not be substituted. Status 3 means unlimited. `2062` omits an absent plan, while `1004` requires auth recovery. A transient plan failure keeps fresh points and uses shared partial-window retention rather than discarding the account.

The plan predicate reports an entitlement hint, not a verified paid-subscription state: workspace or membership `has_token_plan`, or a nonempty tier, enables the quota read. It does not establish payment, auto-renewal, trial status or expiry, and no product-generation classifier consumes `current_subscribe_combo_type`. A quota `2062` removes quota windows but does not override the earlier label; a reported plan name without current quota is not proof of active paid service.

Code's `accountLabel` names the product, never the subscription. The plan cell uses `planLabel`: workspace `token_plan_tier` precedes membership's, and textual tiers need no extra request. Pure-digit tier strings are combo IDs. On the same regional platform origin, OAuth optionally reads `/v1/api/openplatform/charge/combo/cycle_audio_resource_package` with the current group's header and the official `biz_line=2`, `cycle_type=3`, `resource_package_type=7`, `business=Agent`, `device_platform=desktop` query. Only a matching `current_subscribe.curr_subscribe_combo_id` permits a name: prefer the matching `current_combo_card.title`, then `current_subscribe.current_subscribe_title`, ignoring empty or pure-digit titles. A catalog card alone never establishes the current subscription. Name resolution is independent of quota availability and this response is not cached across logins or groups; renderers retain their shared error-state precedence during a quota outage. Missing, denied or malformed optional names retain the generic `Subscription` label without invalidating quota, rotating credentials or selecting another credential; cancellation still cancels collection. API-key subscription rows also use that neutral label because their quota response does not establish the product generation.

Matched current-subscription names may be retained in memory for one hour per credential namespace, region, account group, login epoch and combo ID. Ordinary token rotation retains the name; missing epochs, failures and unmatched catalog responses establish no cache entry. Only the name is retained: personal workspace, membership, points, grant details, plan quotas and API Spend keep their existing collection cadence.

The official generic label can be `M Plan` or `Token Plan` according to catalog availability; neither names a purchased tier. Settings retain the upstream `Token Plan` / `API billing` choices for the manual key. Display only quota authorized by that supplied key; the choice does not establish which product the account purchased. Without a token plan, membership `plan_name` may name the Code membership; it does not establish a Token Plan subscription. Do not derive the Token Plan tier from `personal_plan_type` (Free/Basic/Pro/Ultra), product enums, quota size, point totals or the `MiniMax Code` product label.

Token Monitor reads the official credential and auth-state files without modifying them. It does not exchange refresh tokens, acquire or remove official locks, publish refresh fences, retry credential writes or clear the official login.

When the selected lease has expired, or membership/plan rejects it with HTTP 401/403 or business code `1004`, Token Monitor may invoke the installed official CLI once with `provider list --json`, then reread that same namespace. Healthy, unexpired leases do not invoke the CLI proactively. Missing CLI installations fall back to read-only status until the official client renews the login; never install or update a CLI automatically. The command initializes the official runtime and may create or migrate its configuration/database and shell integration; delegation is not a side-effect-free status endpoint.

CLI lookup uses PATH, the official installer directory (`MCODE_INSTALL_DIR` or the platform default), and existing npm locations. POSIX installers expose `bin/mcode`; Windows installers expose `mcode.cmd` in the install root. A desktop App installation does not establish that the separate CLI exists. Launch Windows shims through cmd with fixed arguments and bound process-tree cleanup; use an isolated private working directory rather than a user's project. No credential is passed in arguments and command output is not published.

The delegated command must receive the selected data root through `MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR` and its `cn`/`en` region through `MAVIS_REGION`. Installation paths are not data paths. The official record account key hashes the absolute auth-home path spelling and client ID: a symlink or other spelling of the same physical directory need not select the same record. Select the exact official record key, allowing stale sibling records; do not switch roots or regions to recover a login. App-only custom data-directory preferences are not discovered automatically: configure the matching data root explicitly when it is outside the shared discovery roots.

A zero exit code or printed provider list does not establish renewal. Require a changed access token, authenticated matching-generation state, an unexpired lease and the same nonempty login epoch after rereading; a replaced login waits for a later normal collection. Legacy records without a login epoch remain readable while healthy but cannot establish delegated recovery ownership. A newer valid lease already published by the official client needs no CLI call. An unchanged, expired token after delegation is unauthorized, following Claude's delegated-recovery precedent; normal polling can retry it without a transient-failure retry loop. `provider list` does not force renewal of every unexpired token rejected by a resource, so an unchanged unexpired credential remains unavailable without repeated attempts in that collection.

Once a delegated command starts, quota cancellation does not interrupt its official rotation. Bound it independently, then honour cancellation before requesting quota. A timeout may leave official recovery pending; never repair its files or remove its locks. Membership and plan share at most one recovery and one resource retry. Missing, malformed or transitional auth state remains unavailable; logout state retains the shared sign-in status. Custom `MCODE_OAUTH_*_ENDPOINT` overrides remain unsupported.

## Account identity and aggregation

Code identity hashes the server's regional group. Manual API-key identity retains its existing key hash. Matching readings select one observation through shared aggregation; amounts are never added across devices. There is no automatic alias or stored-key migration. One current Code login and one API key can coexist locally; multiple managed Code logins are unsupported. Product labels do not replace subscription names in the plan cell.

Only a verified pair suppresses numbered account titles and the account count. Its two observations retain separate standard provider headings, each with its own plan and update time; the relationship never promotes one lane’s plan to the other. For CN pay-as-you-go keys, query `/v1/token_plan/remains?GroupId=<Code personal group>` with the API key: a well-formed success or `2062` (authorized group without a subscription) confirms the display relationship. A `2062` response may have null quota rows; successful code `0` requires the quota array. `1004`, other errors and missing response structure leave it unknown without affecting either reading. Confirmation is reused for the exact key hash, regional Code identity and region; credential probes never perform this lookup. A later resource failure retains the confirmed relationship and region without making that resource healthy. Raw groups stay in main's runtime state. Optional `relatedAccountKey` carries only the verified peer's hash through authenticated stats/sync, is stripped from public stats, and never acts as an identity alias or subscription binding. Either lane may carry the evidence after an account-scoped refresh. New associations are not established in subscription-key mode or other regions; unverified pairs retain ordinary account titles. Normal OAuth rotation and billing-type changes do not change an already verified key/group relationship or require another confirmation.

An identified successful Code reading may retire the prior local OAuth identity through shared removal markers. A failed or unidentified read cannot prove logout or create a replacement account. Scoped work for a retired account must not adopt a newly logged-in account. Use the shared runtime's cancellation/revision checks; removal markers never enter the wire payload.

Subscriptions and top-ups bind to an exact saved account key. A matching label/email or the sole remaining account does not prove the same wallet. Keep saved-only accounts available to the shared settings picker while their live reading is unavailable. Any future cross-source identity change must preserve existing bindings rather than simply replacing hashes.

Provider subscription metadata is separate from saved cost records in `settings.subscriptions`. A detected plan name may prefill the editable cost form, but never creates an expense record, supplies its price or establishes its renewal schedule. Those records still require the user's form submission.

## Regions, settings and shared display

Explicit `minimaxApiRegion` wins over legacy `minimaxApiHost`, then `TOKEN_MONITOR_MINIMAX_API_REGION`, `MINIMAX_API_REGION` and `MINIMAX_API_HOST`. Aliases are exact. An unchosen setting stays empty and resolves the environment at use time; an explicit Auto is stored as `auto`. The wire keeps `cn`/`en`, distinct from settings' `intl`/`auto`.

For API-key sources, Auto first tries the runtime's last region that returned quota windows, or International when none is remembered. A pinned region never crosses regions. HTTP 401/403, business `1004` (including its HTTP 400 form), and transport failures may drive the existing fallback; ordinary 400 errors, 5xx, 429 and JSON errors do not. After a transport failure followed by an auth rejection, report unavailable rather than invalidating a potentially valid key. Remember a region only after a usable reading.

Credentials stay in main and calls use the injected transport. Key billing type and region save independently; credential submission waits for those writes and does not overwrite them from a stale draft. Key, billing-type and API-region edits clear only API readings; they do not select or retire the discovered Code login. Replacing or clearing the local key retires its old API identity without retiring Code. Save-time key validation never reads or renews Code. Browser links follow the selected billing type and pinned or last-successful region through the declared URL policy.

Reuse shared account rows, sign-in states, privacy handling, balance formatting, Spend tooltip and hide/show behavior. Settings keep the automatic connection explanation separate from the key form, like other automatic-plus-manual providers. Either healthy lane keeps the provider summary live, while the key form status reads only the local API lane. Both Code points and the API wallet use `metric: 'credits'` with their own units. The `billing` window kind does not make points currency.

Membership alone supplies no points denominator. Optional active credit details may supply a bar only after complete pagination, valid grant/remaining/expiry fields, exclusion of expired grants, and reconciliation against that same membership total within half a hundredth of a point. Otherwise retain the fresh amount without a bar. Expiry is not spend, and independent grant expiries do not imply one reset date. API wallet meters remain shared display-only values, never wire percentages. Team collection and simultaneous managed Code logins are unsupported.
