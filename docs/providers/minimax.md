## Data sources

`minimaxBillingMode` selects `token-plan` (the default for existing installations), `api` (pay-as-you-go), or `code` (MiniMax Code OAuth). Token Plan keeps its quota endpoints and legacy Coding Plan fallback. API billing queries `/account/query_balance` on the selected MiniMax API host, as implemented in the [official MiniMax CLI](https://github.com/MiniMax-AI/cli/blob/a965e72ce424e465ae65ded102315bf73bef0aa3/src/client/endpoints.ts). It uses `available_amount`, not the cash-only balance, and emits one `credits` window in CNY for China or USD for International. Zero and negative balances are valid responses; missing or nonnumeric amounts are unavailable. No quota percentage, reset time or spend history is inferred.

The `code` tier reads the local MiniMax Code login (the desktop app's OAuth lease, discovered under the [mcode data directories](mcode.md) at `auth/prod/<region dir>/<record dir>/auth.json`) and renews it when needed. Its membership request, `POST agent.minimax.cn/matrix/api/v1/commerce/get_membership_info`, reports `op_credit_summary.total_remaining_amount`: the combined purchased and gifted points, represented once as `CREDITS`, with no money conversion. Purchased/free component amounts must not be added to that total or emitted as extra balances. The same OAuth also queries the Open Platform `/account/query_balance` endpoint and reuses the API balance parser for a separate `API Balance` window in CNY/USD. Wallet refusal or failure does not discard Code points or trigger an OAuth refresh when membership still succeeds. Purchased credits are shared between Code and Open Platform; gifted check-in credits are Code-only. The pay-as-you-go cash wallet is separate. See the [OAuth capability and compatibility checks](../research/minimax-oauth-capabilities.md) and [credit-pool evidence](../research/minimax-credit-pools.md) for source scopes, expiry, purchase endpoints and fallback rules.

Before membership, `POST /matrix/api/v1/user/get_user_extra_info` selects exactly one personal workspace (`workspace_type: 0`) and passes its `workspace_id` explicitly. ID `0` is valid. Missing or ambiguous personal workspaces are unavailable; collection never calls `workspace/update_default`. When membership reports `has_token_plan: true` and an `op_group_id`, Code queries `GET www.minimaxi.com/backend/account/token_plan/remains_percent` (international: `platform.minimax.io`) with the official SDK's `X-Group-Id` header. This endpoint reports used/total percentages, unlike the API-key Token Plan endpoint's remaining percentages. Status 3 means unlimited here; video counts are a separate window. `2062` omits plan windows and `1004` triggers auth recovery. Accounts without a plan skip the request. A transient or malformed plan response keeps the fresh credits and uses the runtime's partial-window merge to retain any prior plan windows with their old timestamp and an unavailable status. With no prior plan windows, the current credits stand alone. Switching account types clears readings rather than adding overlapping pools together.

Billing types never fall back to each other's endpoints. The selected type applies to both the credential-save probe and later collection; key prefixes do not override it. `MINIMAX_CODING_API_KEY` remains the Token Plan environment credential, and no new environment credential is auto-discovered.

## Source precedence

An explicit `minimaxApiRegion` choice wins over the legacy probe option `minimaxApiHost`, then `TOKEN_MONITOR_MINIMAX_API_REGION`, `MINIMAX_API_REGION`, and `MINIMAX_API_HOST`. Region and hostname aliases are exact matches. The default is `auto`: probe the last region that returned parseable quota first, or international first when no success is remembered. The other region remains a fallback for authentication rejection or transport failure. A China/International selection from settings or env always pins that region ahead of memory and prevents cross-region requests.

Within each region, the Token Plan endpoint falls back to the legacy Coding Plan endpoint on the existing migration/error signals. A transport failure skips the remaining endpoint on the unreachable host. Runtime cancellation stops the probe without retrying another region; a per-request timeout remains eligible for fallback. HTTP failures such as 5xx or 429 and JSON parse failures do not trigger a cross-region retry.

## Credentials and transport

The API key stays in the main-process credential store. Region or billing-type changes retain the key, clear the old quota, and immediately refresh only MiniMax through the normal settings invalidation path. Calls use the injected transport and fixed MiniMax API URLs.

The `code` tier has no credential field, no paste panel probe and nothing in the credential store. Discovery reads the official `auth/prod/{cn,en}/mcode-public` namespaces under the [mcode data directories](mcode.md); a pinned region selects one namespace, while Auto prefers China. A namespace contains one current user login, not an account list. The `records` map is keyed by service plus a NUL-separated storage hash; unrelated records are preserved. Both credential and state files are re-read each tick. An authenticated state must match the credential generation; an expired state is refresh input only. Missing state is not configured. Logout/anonymous states require sign-in; authorizing, refreshing, error, schema/domain mismatch or inconsistent generations are unavailable, with no old-token use or exchange.

**Managed refresh.** Refresh (`POST account.minimax.cn/oauth2/token`, international `account.minimax.io`) sends `grant_type=refresh_token`, `client_id=mcode-public`, `scope=agent.default` and `audience=agent-backend`. Observed server grants rotate the refresh token; if a grant omits it, the previous value is retained as the official client does. Bearer type, required scope and positive `expires_in` are validated; short expiry is not extended locally. Scope comes from the grant body or, for JWT-shaped tokens, its scope/scp metadata. Decoded metadata is not used as account identity or token authentication. One exchange serves both proactive refresh inside a 10-minute leeway and reactive refresh after an HTTP 401/403 or body code `1004`, followed by one resource retry. `invalid_grant`/`unauthorized_client` and unusable successful grants invalidate the state rather than replaying an uncertain predecessor token. Any other token-endpoint failure, including HTTP 401/403, restores the previous state and is `unavailable`.

Refresh holds the official client's `auth.lock.lock` directory mutex across the under-lock reread, exchange and synchronous write-back. It skips probes, a running client, failed process detection and busy locks. Before exchange, it durably reserves the next generation with the official `refreshing` transaction ID/owner shape. Writes require both that exact state fence and the original-or-updated credential lease. The authenticated state is published last. Lock identity is checked before commit, rollback and release; replaced and abandoned locks are not stolen. Ordinary failed exchanges restore the previous state only under the same lock and transaction; an expired or missing access token is never used as fallback.

The existing private atomic writer preserves other records. Successful grants with a transient write failure remain in main-process runtime state, bound to their transaction, for write retry. State/lease changes discard that pending grant instead of overwriting logout or a new login. Token Monitor does not copy the official refresh journal: a crash before the new credential reaches disk loses a memory-only grant, but the durable fence prevents replay of the old refresh token. Official Core can recover a matching committed generation, or invalidate a dead owner without one. A separate re-login may still be required after an interrupted grant. Compatibility was executed against the extracted official 3.1.6 Core with fake credentials; see the research note.

Successful Code rows hash the server's regional `op_group_id` for account identity. The local record key hashes the storage namespace, so it is not an account ID and must not identify readings across devices or re-login. Missing GroupId leaves identity absent and skips plan requests; it does not invent an account from a local path.

If the fallback region rejects the key after a transport failure, report `unavailable` so the runtime retains the last known quota instead of prompting for a replacement key. When every attempted region rejects the key without a transport failure, report `unauthorized`.

## Invariants and known gaps

An unchosen region stays empty in stored settings. Renderer projection and runtime config resolve the environment at use time; displaying Auto or saving a key must not freeze an implicit default. An explicit Auto selection is stored as `auto` and overrides the environment. The form's region saves independently (`submitWithCredential: false`); writes are serialized per field, and key submission waits for queued writes and omits the region from its credential draft. Failed writes show a panel message and leave the queue so later submissions can retry after settings resync.

The data-source select (the existing `minimaxBillingMode` key) also saves independently and stays visible after linking. Credential submission waits for that save and omits the type from its draft, so a stale renderer value cannot override the saved selection. The `code` tier shows its local-login instructions beside the selects and hides the API-key panel, Save, Clear and web billing link. Refresh stays available. Its connected/re-login state follows the OAuth row rather than the saved API-key flag. The settings pill and the settings-row tag use the shared sign-in labels; the limits card keeps the shared short status labels. The code note is the only Code-specific sentence. The main-process save boundary rejects key submissions in Code mode before probing, so a healthy local login cannot validate an unrelated key. Switching back retains the saved key for the API-key tiers.

On the `code` tier, `has_valid_subscription` is unreliable; membership `has_token_plan` controls the plan request. Code points always use `CREDITS`; the API wallet uses its own money unit, so the amounts are never added together. Points have no allowance, so the window sets `showMeter: false` and the card shows the amount. The API wallet omits that flag and keeps the shared display-only balance meter; that percentage is not written onto the wire. Plan rows are the shared session and weekly percentage meters. Video is another weekly window: its percentage is the headline and its count is the shared detail line. Both balances use `metric: 'credits'`, so they are one visible-usage item, the same way two credits windows already share that id. Purchased and gifted points stay inside the one total. The `billing` kind is the shared balance container, not an indication that points are currency. Code currently reads the personal workspace. Team collection and simultaneous managed logins are not implemented. The official CN/international origins and `cn`/`en` namespace names are source-verified; international accounts and Windows/Linux remain untested live.

Open Browser follows the current China/International selection, including before the first successful probe. Auto follows the last successful probe's `en`/`cn` region, with the historical China landing page until a successful result exists. The wire region keeps `en`/`cn`; the setting's `intl`/`auto` vocabulary never replaces it.

The API-key tiers’ browser path follows the billing type: Token Plan opens its plan page, and API billing opens the balance page. The descriptor's `pathByField` uses only declared paths, validated against the provider URL policy for every region.

Region memory lives in the runtime's `providerRuntimeState` and resets with a new runtime. Only responses with quota windows update it; unavailable responses leave the last successful region intact. Changing a key can still resolve the other region through Auto's fallback.
