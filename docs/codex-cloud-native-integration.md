# Cloud sessions in the existing Sessions view

Cloud is a session source, not a separate application view. Local Codex, hosted Codex, dot tasks and subagents appear together in the existing **Sessions / 会话** list, using its renderer, recency sorting, pagination, keyboard behavior and detail surface. There is no Cloud footer button or Cloud dashboard tab. The ordinary dashboard retains Overview and Trends.

`cloudSessionRows.js` adapts the current account-checked observer snapshot to the existing session row shape. Cloud-only rows keep the Codex tool identity and add a small **Cloud / 云端** source label and a cumulative source metric. Cloud tasks without model/rate data show a pending fee. They do not fabricate a model name, session title, request count, generation speed or price. A missing token counter remains unavailable. The normal row's detail opens the observed numeric breakdown, last observation/activity time, engine-parent and delegation-parent identities, connection gaps, and whether the thread's counters are included in the headline total (and, when not, why). It does not request a local transcript for a cloud-only session.

An exact canonical Codex thread UUID shared by a local and cloud record produces one local row labeled **Local + cloud / 本地 + 云端**, with cloud observations appended to its detail. Local titles and requests remain intact; comparable cloud usage tops up the headline by only the amount missing locally. Local known prices and unknown-price markers are preserved. UUID-looking fragments inside a rollout filename or title are not enough to identify a duplicate. Other tools never collapse into Codex merely because their IDs match.

## Counting, dates and privacy

The account ledger adds an Electron-only presentation overlay: eligible cloud counters **do** join the headline TOTAL / DAY / MONTH through the Electron presentation path, on top of the collector's own aggregation. `cloudLedgerRuntime.js` polls every five seconds the observer's `report.json` (and an existing `native-previous-report.json`, if present, for first-run seeding) and persists `cloud-ledger.json` beside them in the observer data directory — mode 0600, written with an fsync'd temp-file rename. The ledger is keyed by the account scope fingerprint, so accounts never merge, and that fingerprint never crosses into the renderer. The runtime reads what the independent launchd observer already wrote; it never opens a cloud connection, never starts a model turn and collects no message text.

The accounting contract:

- The **first** valid cumulative snapshot of a thread is a lifetime baseline. It contributes to TOTAL only — never to DAY or MONTH — because the tokens predate observation.
- Later monotonic differences contribute to TOTAL (always) and to DAY/MONTH while within the local calendar range, dated by the observation that saw them (the thread's own event time when it is valid). Repeated cumulative snapshots are idempotent and never summed; an increment observed while the app was closed is dated at the observation that bridged it and the thread is flagged.
- Cached input is included in input and reasoning output is included in output; increments keep that relationship, and the period component split closes over the added total. A missing counter stays unknown: the total still counts only when input and output are both known, and unknown cache/reasoning components mark the thread partial rather than being split arbitrarily.
- A decreasing counter keeps the last high-water anchor and marks the thread partial. Returning to an old cumulative value adds nothing; only growth beyond the retained anchor can count. Invalid or unsafe observations freeze the affected contribution. Corrupt persistence is preserved, recording pauses, and any readable retained values are explicitly incomplete; the original is never silently replaced.
- No historical daily reconstruction: nothing before the first observation is dated into a day, and pruning day buckets older than 62 days only narrows the recent view (all-time sums live on the thread record).

### Deduplication and overlap policy

Cloud counters are reconciled with canonical local records per comparable period, and the overlay lives entirely in the main process — Hub ingest, `/api/public/stats`, the headless agent and the device wire shape are untouched, so an account observed by the same ledger on two machines cannot double count through the Hub (each machine overlays only its own ledger). Exact identity means the canonical Codex thread UUID: the whole `sessionId`/`threadId`/`canonicalSessionId` value or the `codex:<uuid>` key. A UUID-looking fragment inside a rollout filename, title or label is never proof of shared identity, and other tools never match. A comparable local/cloud match forms a max union: cloud 100 and local 80 add only 20; local subsequently reaching 110 removes the cloud remainder and the combined result is 110. A local DAY value never substitutes for an unknown all-time value. Missing comparable totals conservatively exclude that period and mark incomplete coverage. The component split of a reconciled remainder stays unknown rather than being prorated. Conflicting identity aliases never merge. A thread whose engine or delegation parent is present in the same ledger and contributes counters is conservatively excluded as parent/child overlap (a fork may also inherit earlier history); the child counts once the parent contributes nothing. Excluded and partial threads, their reasons and the counted amounts are exposed as the bounded `cloudAccounting` block in stats and explained in the Sessions note, the cloud detail and the one-line note under the headline total. Unknown model attribution and chargeable cloud fees are never invented. Aggregate unsafe integers are excluded with partial coverage; capacity pauses recording instead of deleting another account or current-period history. Changes to parent metadata, account scope, status and local dates invalidate the presentation cache even without new counters.

DAY and MONTH select which cloud *rows* are listed by source activity time (creation time only when activity is unavailable), not by the time an old token snapshot was replayed; a row's own visible value stays explicitly cumulative. Unsupported derived ranges retain the existing session-availability gate. The headline total moves automatically whenever the ledger changes, without Sessions or Settings being open.
The opt-in local Dots executor collector from #944 is a separate source: `usageSource: codex-dots-local`, `usageCoverage: observed-only`. Its actually observed local turn usage continues into periods, models, projects and history through the upstream collector. It does not count cloud coordination or reconstruct offline gaps. When the same canonical thread also has a cloud snapshot, Sessions keeps the local period value, title, cost and unpriced-token marker in one row and adds the separate cumulative cloud detail. Repeated cloud snapshots never add to the local contribution. The upstream native-rollout precedence remains in effect before presentation, so a native-backed thread does not also contribute its supplemental Dots ledger usage. A cloud-account rejection removes only the cloud annotation; it does not erase local Dots usage.


The main-process bridge still uses a fixed report path, size and row limits, token validation, account-scope checking before/after a read, and a field allowlist. Credentials, scope fingerprints, private paths and raw messages never enter the renderer. Sender checks require an owned top-frame bundled renderer. Stopped/expired observations are not marked live; a mismatched login clears cloud rows and detail data. Installation-retained values keep their earlier timestamps and are labeled as prior observations, not new consumption.

The UI reads this bridge serially while Sessions or Settings is visible. It does not open cloud connections or launch a second watcher. The background automatic discovery/event capture service remains unchanged. Its toggle now lives under **Settings → General → Integrations → Automatically monitor Codex cloud sessions**, not in a cloud-only screen. Closing the application does not stop the independent user service; disabling the toggle does. Legacy `cloudUsage:open` IPC and `--cloud-usage` command arguments navigate to Sessions for compatibility; `--sessions` does the same.

## Verification

```sh
node --test tests/shared/codexCloudAccounting.test.js \
  tests/electron/cloudAccountingRuntime.test.js tests/electron/cloudAccountingRegression.test.js \
  tests/electron/dotBilling.test.js tests/electron/cloudSessionRows.test.js \
  tests/electron/cloudUsageIntegration.test.js
TM_SESSIONS_VERIFY_DIR=/absolute/private/test-directory \
  node_modules/.bin/electron scripts/verify-unified-sessions.js
npm run verify
```

The ledger tests cover cumulative replacement and idempotency across restart/reconnect, prior-report seeding, account isolation, decreasing/invalid/corrupt state, exact local/cloud identity dedup, parent/fork overlap exclusion, date boundaries, component arithmetic and overflow. The UI smoke harness uses the actual main-window HTML, preload and renderer, with entirely synthetic session/stats responses. It checks mixed local/cloud rows, the cloud-inclusive header total and its accounting note, the cloud detail's counted-in-total label, an automatic main-process stats republish while the Home view is open, live row updates, source activity period selection, absence of local transcript reads for cloud-only sessions, and the Settings toggle. It creates no cloud connection or model turn.

The screenshot in `docs/images/codex-unified-sessions.png` uses illustrative fixture data. It is UI evidence, not a new real-account token measurement. Prior cloud-engine and automatic-discovery experiments are recorded separately; they do not validate installation of this corrected UI on a disconnected device.

The service toggle controls the existing macOS user LaunchAgent and is disabled if unavailable. This proposal installs no service, enables no observation on first launch, and changes no release/update policy. Cloud observation remains experimental and opt-in. Synthetic regression evidence does not establish real-account completeness, real LaunchAgent fault recovery, or signed application acceptance.
