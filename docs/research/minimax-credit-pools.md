# MiniMax credit pools: current evidence

Research checked 2026-10-24 against MiniMax public product pages and service terms, plus the MiniMax Code 3.1.1 bundle and the running 3.1.6 account UI. The current UI directly confirms the sharing, validity and deduction rules below. The current app bundle gives more specific source-scope rules than the public migration guide, so this note distinguishes the account total from which services may spend each credit type.

| Question | Evidence | What it establishes |
| --- | --- | --- |
| Do MiniMax Code users receive free credits? | The [MiniMax Code product page](https://agent.minimax.io/download) describes daily login credits. The app UI asset `88822-3dfac7ee1840c08d.js` identifies check-in rewards as gifted credits and gives them a 30-day validity. The [Agent service terms](https://agent.minimax.io/doc/en/credit-rules.html), last updated 2026-02-11, also describe daily rewards and older Member/Bonus/Reward categories. | Free credits exist. The current app treats check-in rewards as gifted credits with a shorter validity than paid credits; do not assume they have the same API eligibility. |
| Are free grants and purchased credits summed in MiniMax Code? | The app parser in `60966-12f8280f4dd2219f.js` reads `total_remaining_amount`, `purchased_remaining_amount`, and `free_remaining_amount`. Settings UI in `11842.73ddd5bcb6e0b9d7.js` displays purchased and free components together under MiniMax Credits. The filtered read-only capture at `/tmp/minimax-credit-pools-evidence.json` reported total 4,624, purchased 0, and free 4,624 for a migrated account without a Token Plan. Seven detail rows were all `credit_type: 2`; six active rows summed to 4,624, while an expired 347.91 row was excluded. | Yes, the current Code summary/UI presents purchased and free credits as components of one total. This account had no paid credits, so it does not provide a paid-purchase before/after observation. The endpoint total must not be labeled sign-in-only. |
| Which credits are shared with the Open Platform API? | The current app tooltip in `88822-3dfac7ee1840c08d.js` says M Plans and paid credits are shared between MiniMax Code and Open Platform, while gifted credits such as check-in rewards are MiniMax Code-only. The public [billing migration guide](https://agent.minimax.io/doc/en/billing-upgrade-en.html) says the old Agent Credits became MiniMax Credits and describes the balance as interoperable with Open Platform API. | Use the current app's narrower source split: M Plan entitlements and paid credits cross to the API; gifted check-in credits stay Code-only. The migration guide describes the unified balance during migration; it does not make every credit source API-eligible. A Code total may overlap an API paid-credit reading. |
| Are plan quotas separate, and how does fallback work? | The app tooltip in `88822-3dfac7ee1840c08d.js` describes M Plan > Credits, with fallback after the 5-hour or weekly plan limit. When enabled, credits are used after the plan limit; the setting can be disabled in Settings. The setting label is “Use Credits after M Plan limit,” and the client reads `token_plan_credit_fallback_enabled` in `60966-12f8280f4dd2219f.js`. The updated safe capture at `/tmp/minimax-credit-pools-evidence.json` records this flag as `true`. The tooltip says eligible credits, including gifted credits, are drawn by expiration order. | Plan quota and credits are separate. Code fallback is configurable and is enabled for the observed account; it can spend eligible credits after a 5-hour or weekly limit. There is no documented paid-first or gifted-first priority; the UI specifies expiry order. |
| Why do plan endpoints show zero when membership shows 4,624 credits? | In the same safe capture, `/backend/account/token_plan_credit` reports `remaining_credits: 0`, `balance_breakdown.total_balance: 0`, and no buckets; `credit_auto_billing` reports current and subscription balances of 0. The modern `remains_percent` response succeeds with `base_resp.status_code: 0` but has no `model_remains`. The account summary has `hasTokenPlan: false` and membership credits of 4,624. | These are plan-credit/quota and auto-billing views, not a second reading of the membership credit balance. Zero or absent plan data does not contradict or replace the separate membership total. With no Token Plan, no plan quota rows are available from `remains_percent`. |
| Do MiniMax Credits share the API cash wallet? | The current [M Plan page](https://www.minimax.io/m-plan) says a Subscription Key draws on M Plan usage and credit packs, while the account balance is charged only for a pay-as-you-go API Key. The [paid-services agreement](https://platform.minimax.io/protocol/paid-agreement) treats Token Plan Subscription Keys and standard pay-as-you-go API Keys as distinct credentials and billing modes. | Paid credits may be shared with eligible Open Platform API use, but the pay-as-you-go cash account balance is separate. “Shared with API” does not mean “same as API wallet.” |
| What are the current expiry rules? | The app tooltip says paid credits expire in one year and check-in gifts such as daily rewards in 30 days. The public [migration guide](https://agent.minimax.io/doc/en/billing-upgrade-en.html) assigns one-year validity from migration to converted Agent Credits. | Expiry is grant-specific. Do not assign one reset date to the combined balance; the migration rule applies to converted credits, while the app distinguishes paid and gifted credits. |

| What changed in the migration? | The public [billing migration guide](https://agent.minimax.io/doc/en/billing-upgrade-en.html) converts remaining Agent Credits by original purchase value, provides some migration rewards, and maps or cancels old Agent subscriptions by plan status, term, and payment channel. Current [M Plan](https://www.minimax.io/m-plan) offers Go/Explore/Build; older Token Plan pages used Plus/Max/Ultra. The observed account is marked `migrated: true`. | Do not map old Agent Basic/Pro/Ultra or Token Plan Plus/Max/Ultra names directly to current M Plan tiers without checking the account's migration record. The public migration guide has no visible revision date, and MiniMax serves different page variants. |

## Implementation implications

- Keep the membership summary's total as one MiniMax Code credit amount; do not also emit its purchased/free components as extra balance rows. Use the component fields when showing the split. Do not call the total sign-in-only.
- When comparing with an Open Platform reading, account for overlap: paid credits may be the same balance, while gifted check-in credits are Code-only. Keep the pay-as-you-go cash balance in its own money pool.
- Keep M Plan quota windows separate from Credits. The Code setting controls whether eligible credits cover usage after the 5-hour or weekly plan limit; do not add quota capacity and credit balance together.
- The repository's display-only `creditsMeterPercent()` can show a positive balance as 100% when no spend or denominator is available. That is not a service-reported quota percentage. For MiniMax Credits, show the amount and leave percentage unknown unless MiniMax supplies a meaningful denominator or percentage.
- The safe capture showed zero purchased credits, zero Token Plan credit pool, and zero auto-billing balance, while the membership summary had 4,624 free credits. Its `token_plan_credit_fallback_enabled` value is `true`; no purchase was made, so post-purchase behavior remains unobserved. The successful `remains_percent` response had no `model_remains` because the account has no Token Plan. These zero/empty plan endpoints are not the membership total. The app UI says expiry order, so do not claim a paid-first or gifted-first deduction rule.
